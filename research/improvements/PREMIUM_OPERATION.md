# 艇ろぐプレミアムの試用と公開

レースのプレミアムタブと、マイノートの週・月・年収支グラフは同じ会員状態を使います。公開HTMLには見本のみが入ります。会員限定の集計値はEdge Functionでログインと契約を照合した後に返します。

## データを更新する

直近3節相当の公式履歴を使い、モーターの使用期をまたぐ走りを除きます。同じレースの6艇平均との差を集計し、新しい走りほど重くします。少なくとも6走・3日、同じ場で比較対象が12基そろう項目に試験評価を付けます。Sは上位5%を目安に、場の中央値から所定の秒差があり、別節と複数の乗り手で再現した場合です。展示と直線のS〜Dは試用向けです。今節の組み合わせを評価する項目は、下記の別の基準を使用します。

```sh
python -m scraper.premium_motor --output private/premium.json
python -m scraper.premium_motor --publish
```

2番目は、既存の日次履歴更新の成功後に実行します。直前の日付の各場で予定レースの9割以上に確定結果が必要です。件数不足は失敗として報告し、再試行します。保存済みと同一の送信は成功扱いになります。別の内容で同日を置き換えたり、古い版で最新を上書きしたりする操作は拒否されます。35日前までの日次版を保持し、各レースではその日より前の版を使います。

環境変数 `TEILOG_PREMIUM_FUNCTION_URL` は既存のSupabaseプロジェクトの `/functions/v1/premium` URL、`TEILOG_PREMIUM_PUBLISH_KEY` は64文字のランダムな16進文字列です。後者は実行元とEdge Function双方の秘密設定に登録してください。公開履歴から計算するため、映像・個人ノートは使いません。

試用配備後の定期運転には、homesvの作業専用アカウントに独立した浅いチェックアウトを置き、`bash tools/publish_premium_daily.sh` を実行します。午前8時から数回再実行できるようにすると、日次履歴が遅れた日も拾えます。同じ締め日の更新が成功した場合、それ以降の定期実行は送信を省略します。環境変数は作業用アカウントだけが読める設定で渡し、ログには終了結果だけを残します。公開先・鍵を登録するまでは手動の `--output` で検査します。

## 別の乗り手での試験

公式履歴で10/29・11/4・11/8を締め日とし、次の4〜6日間の初見の乗り手の走りを場・号機・選手単位で平均しました。3期間とも、過去の秒差をそのまま予測値にすると6艇平均を使う場合より誤差が増えました。過去の差を25%まで縮めた試行では、平均絶対誤差は展示で約4%、直線で約1%減り、まわり足は3期間とも悪化しました。25%は同じ履歴で比べた値であり、独立した検証は今後必要です。まわり足はこの評価から外し、Sを含む他の評価も試用表示にとどめます。

## Supabaseと決済

既存の会員対応マイグレーションに続けて日次版とオーナー用のマイグレーションを適用し、Edge Function `premium` を配備します。関数はリクエスト内で本人の認証または専用の更新鍵を検証します。Supabaseの配備で関数の組み込みJWT検証を無効にする場合も、コード内の認証を有効にしたままにします。

| 秘密設定 | 用途 |
| --- | --- |
| `TEILOG_PREMIUM_TEST_USERS` | 試用に招く既存アカウントのID。複数はカンマ区切り |
| `TEILOG_BILLING_MODE` | 決済未設定時は空。試験は `test` |
| `TEILOG_STRIPE_SECRET_KEY` | Stripeの秘密鍵 |
| `TEILOG_PREMIUM_LIVE_APPROVED` | 本番販売の確認がそろった後だけ `true` |
| `TEILOG_STRIPE_PRICE_ID` | JPY月額プランのStripe価格ID |
| `TEILOG_STRIPE_PREVIOUS_PRICE_IDS` | 旧料金の有効な契約を認める場合の価格ID。複数はカンマ区切り |

オーナーは本人確認した既存のログインIDを管理側で専用表に登録します。オーナーは決済なしでレースの評価と収支グラフを利用できます。決済未設定のときは招待アカウントも試用できます。テスト決済モードでは、招待アカウントだけがテスト画面を開けます。テストで支払いに失敗した場合は会員権限が付きません。契約は画面を開くたびにStripeで照合するため、申込画面から戻るURLだけでは会員になりません。支払い設定と解約はStripeの会員ページを使います。

別期間の検証は `python -m scraper.premium_validate --window <締め日> <検証最終日>` で再現できます。締め日までにその号機を使用していない選手の後日成績を比較します。

実際に受付を始める前に、決済の取扱可否・最終料金・事業者表示を確定します。無料ログインと試用アカウントで公開ページと会員向けAPIの見え方を検査し、テスト決済の申込・失敗・解約・会員解除を確認します。

## 今節のまわり足と立ち上がり

- まわり足は各場の公式まわり足を使い、同じレースの6艇平均との差を「今節・同じ選手・同じ号機」で集計する。最少3走かつ2日。最近最大4節の同じ場の組み合わせと比べてA〜Dを付ける。検証でA〜Dの平均が順に並んだ20場で生成する。江戸川は公式値がなく、津・住之江・丸亀は順序が再現しなかったため保留。
- 立ち上がりは、出口側の計測区間を公式資料で確認できた平和島・福岡を対象にする。出口側の直線と通常展示について、それぞれ6艇平均との差を取り、差し引いた相対指数を表示する。指数の単位はpt。加速度、出口直後だけの秒数、モーター単体の評価はこの方法では求めていない。
- 2項目とも今節の組み合わせだけに表示する。対象外の場、比較対象12組未満、選手・開催名不一致、最後の観測から4日以上では保留。Sと総評の確定には追加検証が必要。

2026/10/12〜11/12の4期間で、組み合わせごとに最初の検証日を取り、その日より前の3走以上の平均を半分に縮めて予測した。6艇平均との差を一律ゼロと置いた場合に比べ、平均絶対誤差はまわり足（延べ3,930組）で各期間約8〜10%減少。出口側の参考指標は平和島（187組）で約9〜14%、福岡（228組）で約3〜13%減少した。同じ履歴を使った過去検証で、pt表示の係数はこの試算に合わせたもの。次節・別選手への再現性を保証する結果ではない。

- [BOAT RACE公式の通常展示の測定区間](https://www.boatrace.jp/owpc/pc/extra/enjoy/guide/level2/l2_01_02_07.html)
- [平和島の公式資料](https://www.heiwajima.gr.jp/br04book/pdf/br04book_pc.pdf)
- [福岡の公式資料](https://www.boatrace-fukuoka.com/uploads/pdf/keikotaisaku.pdf)

新項目を含むデータは、新項目を検証するAPIを配備してから、次に確定した日次版で反映する。保存済みの日次版は従来形式のまま読み取れる。


### 実際のA〜Dの翌日検証

`python -m scraper.premium_pairing_validate --start 20261012 --end 20261112 --by-venue` で再現できる。各日の評価を前日までのデータだけで作り、今節の選手・号機の組み合わせごとに、評価が初めて出た日のタイム差を集計した。場の採用判断と同じ期間のため、今後の開催での確認が必要。

| 項目 | 組数 | 節数 | AとDの翌日の平均差 |
| --- | ---: | ---: | ---: |
| まわり足 | 3,269 | 77 | 0.1636秒 |
| 立ち上がり・平和島 | 143 | 4 | 0.0933秒相当 |
| 立ち上がり・福岡 | 143 | 4 | 0.0411秒相当 |

まわり足はAとDがともに出た75節すべてでAが速く、節単位の再抽出による差の95%区間は0.1455〜0.1826秒だった。立ち上がりの差は出口側と通常展示の相対差から計算し、各場の加速度や出口直後の実測秒数には換算しない。場別の検証は各4節なので、販売判断には事前に基準を固定した次の開催での確認を使う。
