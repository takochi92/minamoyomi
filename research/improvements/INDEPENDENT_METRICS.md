# 独自データ（展示動画の実測）の土台

公式が出していない項目を、展示動画の実測で埋めるための「受け取る側」。動画の解析そのものは自宅サーバー側で行い、ここは数値を受け取ってモーター評価にするところまで。

## 最終の形

- プレミアムの全項目（展示・伸び・まわり足・立ち上がり・総評）を、根拠のある数字で埋める
- 毎晩、その日の展示動画を解析して数値を足し、評価を更新する（全自動）
- 部品交換も記録して、変化を見る
- モーターが入れ替わったら、旧モーターの数字は引き継がない

## 守るルール（`scraper/independent_metrics.py`。すべてテストあり）

| ルール | 中身 |
|---|---|
| 身元のない数字は入れない | 日付・場・R・艇・モーター・選手・項目・秒・計測の設定名がそろった行だけ |
| レースの中で比べる | 秒をそのまま比べない。同じレースの平均との差にする（5艇以上測れたレースだけ） |
| 選手ぶんは**引くだけ** | その選手の「いつもの差」を引く。足さない。強い選手をひいきしない（人気薄が乗る良いモーターを見つけるため） |
| 直近3節だけ | 終わった節の新しいほうから3つ。古い節は貯めない。新しい走ほど重い（半減45日） |
| 旧モーターを引き継がない | その場の使用開始日より前の行は使わない。開始日が不明・保留の場は何も出さない |
| 根拠が足りなければ空欄 | 6走・3日・乗り手2人・その場のモーター12機以上。足りない項目は出さない |
| 公式が先 | 公式の数字がある項目は公式。ない項目だけ独自データで埋め、どちらかを必ず記す |
| 部品交換 | 交換日と、交換後の走数を評価に添える（交換で評価を切り直すかは未検証） |

組み分けは場の中での順位：上位20% A／50% B／80% C／残り D。S は上位5%かつ、2つの節・2人の乗り手で再現したときだけ。

## 水しぶきに強い時刻の出し方（`robust_crossing`）

線をはさむ2コマではなく、前後のたくさんのコマに直線を当てはめて通過時刻を出す。直線から大きく外れたコマ（水しぶき・追跡の失敗）は捨てる。当てはめの残差が大きい（6px超）、コマが足りない、向きが逆、線に届いていない走は**欠測**にする。

## 毎晩の流れ

```sh
# 1 動画の解析（自宅サーバー側）→ rows.json を作る
# 2 貯める（同じ入力を2回入れても変わらない。直した値は置き換え）
python -m tools.independent_metrics ingest --store PRIVATE/metrics --input PRIVATE/rows.json
# 3 評価を作る（使用開始日は、モーター一覧と同じ台帳から。保留の場は飛ばす）
python -m tools.independent_metrics rate --store PRIVATE/metrics --through 20261112 --output PRIVATE/ratings.json
# 4 出す前の確認：前の乗り手までの数字が、次の乗り手を当てられるか
python -m tools.independent_metrics validate --store PRIVATE/metrics --through 20261112
```

`rows.json` の1行：

```json
{"date":"20261112","venue":"03","race":12,"boat":4,"motor":61,"rider":"4321","metric":"turn","seconds":3.842,"source":"video","profile":"03-first-turn-v1","parts":["リング"]}
```

`metric` は `exhibition`・`straight`（伸び）・`turn`（まわり足）・`acceleration`（立ち上がり）。`parts` はその日の公式の部品交換。

## 出してよい項目の条件

`validate` の相関（前の乗り手まで → 次の乗り手）が 0 に近い項目は、モーターではなく選手やその日の数字。モーター評価として出さない。公式データでの目安：展示 0.25、直線 0.09、総評 0.13、**まわり足はほぼ 0**（公式のまわり足タイムはモーターの成分が出ない）。動画のまわり足・立ち上がりも、まずここを確かめる。

## 自宅サーバー側（動画の解析）に必要なもの

1. 艇を追う：艇番の色のかたまり、または進む向きの先頭のふち（水しぶきは後ろと横に出る）。毎コマ同じ場所を追えていればよい
2. 線は水しぶきの少ない所に置く（ターンの頂点を避ける）。全コマ（1/30秒）を使う
3. 通過時刻は `robust_crossing` と同じ考えで出し、怪しい走は欠測にする
4. 平和島など公式データのある場で答え合わせをしてから、江戸川など公式データの少ない場へ広げる
5. 過去の展示リプレイが何日前まで見られるかを確かめる（残っていなければ、今日から毎日貯める）

## まだできていないこと

- 動画の解析の自動化（艇の自動追跡）と、毎晩の実行の設定
- 独自データをプレミアムのスナップショット・会員ページへ載せるところ
- 部品交換で評価を切り直すかどうかの検証
- 総評に独自データをどう混ぜるか（項目ごとの検証のあと）

## 全部そろわなくても評価する（2026-11-14 追加）

1回の展示で6艇そろう必要はない。同じモーターは1日に1〜2回走り、直近3節で見るので、測れた走を積めば相対的な順位は出る。

- 2艇以上測れたレースを使う。測れた艇の平均を引くだけだと「速い艇と一緒に測られたモーター」が損をするので、**レースの水準とモーターの水準を同時に推定**する（`race_deviations`）
- 出走機会の4割未満しか測れていないモーターは評価しない（特定の艇ばかり落ちると偏るため。`venue_ratings(starts=...)`）
- **緩めるのは「何走そろえば評価するか」だけ。1走ごとの数字を採用する基準は緩めない**

試算（1場60機・3節×5日×12R。モーター差の標準偏差 0.015 秒、選手差 0.02 秒、走ごとのばらつき 0.03 秒、計測誤差 0.008 秒と仮定）：

| 取得率 | 評価できたモーター | 本当の順位との一致（順位相関） | A以上のうち本当に上位1/3 |
|---|---|---|---|
| 100% | 54機 | 0.69 | 71% |
| 70% | 53機 | 0.63 | 67% |
| 50% | 40機 | 0.60 | 65% |
| 40% | 22機 | 0.53 | 71% |
| 30% | 評価できず | | |
| 70%・1号艇は全滅 | 50機 | 0.61 | 68% |
| 50%・1号艇は全滅 | 24機 | 0.46 | 49% |

目安：**取得率 5割以上**。1号艇がまったく測れない場合は 7割以上が要る。全部測れても順位相関は 0.69 どまりで、これは走ごとのばらつきによる（計測の問題ではない）。

## 艇を1コマずつ追わない測り方（`scraper/kymograph.py`）

艇首の特徴は、次のコマで消えたり別の部分へ乗り移ったりする。そこで、コマどうしの対応づけをやめる。

1. 艇が通る水面の帯で、各コマを「横1列の、水面との差」にする
2. 時刻順に積むと、横＝位置・縦＝時刻の画になり、艇は斜めの帯として写る
3. 帯の先頭のふちを各時刻で取り、`robust_crossing` で直線を当てはめて、線を通る時刻を出す

- 色は使わない。水しぶきで消えたコマは、点が1つ減るだけ
- 水しぶき対策：水面より**暗い**画素だけを使う版（`spray_guard`）。水しぶきは水面より明るく、艇体は暗いことが多い（実映像では未確認）
- 同じ点を追えているかの確認：先頭・中心・後ろの3つで区間タイムを出し、0.02 秒以内で一致すること。帯の幅が急に変わらないこと。外れた走は理由つきで欠測
- 2艇が同時に映っても、帯ごとに別の艇として分ける
- 途中で解像度が変わったコマが混ざると止まる（`frame_resolution_changed`）

```sh
python -m tools.boatcast_kymograph build   --manifest PRIVATE/manifest.json --band 250,330 --output PRIVATE/pass.npz --png PRIVATE/pass.png
python -m tools.boatcast_kymograph measure --dump PRIVATE/pass.npz --gates 357,73 --direction -1 --output PRIVATE/pass.json
```

**半自動（自動で取れないとき）**：`pass.png` を人が見て、艇の帯の先頭のふちを、各線の近くで3点ずつクリックして `clicks.json` にする。`assisted` がそこから区間タイムを出す。1コマずつ読むより速く、検証用のデータにもなる。

```sh
python -m tools.boatcast_kymograph assisted --clicks PRIVATE/clicks.json --gates 357,73 --direction -1
```

テスト用に作った画（暗い艇＋後ろに明るい水しぶき、コマ抜け3割）では、20回中16回以上が測れ、誤差は 0.02 秒未満。**実映像では未確認。**

## ふちではなく「速さ」を測る（2026-11-14 追加。実映像の結果を受けて）

実映像（平和島11R・4号艇）では、暗い画素の時空間図で前半は斜めの帯が見えたが、後半は引き波や水面の模様と重なり、ふちを両方の線まで追えなかった。半自動のふち読みも、手読みと区間で約0.11秒ずれた（直線への当てはまりが良くても、同じ部分とは限らない）。

そこで、帯の**傾き（速さ）**を測る（`kymograph.align` / `measure_speed`）。

- 引き波や模様はほぼその場にとどまり、艇だけが横に動く
- 各行を「艇が進んだぶん」戻して重ねる。速さが合うと艇だけがくっきり重なり、動かないものはぼやける
- いちばんくっきり重なる速さ（と加速）を探す。艇全体の模様を使うので、どの部分を測るかの問題がない
- 採用の条件：くっきりさが他の速さの4倍以上／奇数行だけ・偶数行だけで求めた速さの差が 6px/秒以内／探索範囲の端でない

```sh
python -m tools.boatcast_kymograph speed --dump PRIVATE/pass.npz --gates 370,270 --direction -1 --speeds 120,260 --window 267.7,270.3
```

区間タイムは、求めた動きから「その区間を進むのにかかる時間」として出す。帯がきれいに見える範囲（例：x=370→270）で測るのが前提で、元の長い区間（x=357→73）と同じ物理区間ではない。公式タイムとの比較は、区間の対応を確かめてから。テスト用の画（艇の後ろに、その場にとどまる暗い模様）では、8回とも速さの誤差 1.5px/秒以内・区間の誤差 0.005 秒未満。**実映像では未確認。**

## 実映像の結果と、いまの判断（2026-11-14）

平和島 2026-11-12 11R・4号艇（480p・1080p 各2回。取得は全コマ一致で再現）。

| 方法 | 実映像の結果 |
|---|---|
| 色＋背景差分で追う | 候補が毎コマ複数。最長24コマで途切れる |
| 暗い輪郭＋連続性 | 2回とも 1.5225 秒。ただし23コマ抜け、通過時刻が手読みより遅い |
| 艇首の特徴を追う | 終了線は 0/15 |
| 時空間図のふち（`measure`） | 前半は帯が見えるが、後半は引き波・水面の模様と重なり欠測 |
| 半自動のふち読み（`assisted`） | 1.4399 秒。手読みの目安 1.550 秒と 0.11 秒ずれる |
| 速さをそろえる（`measure_speed`） | 480p 0.64 秒・1080p 0.47 秒。**不合格**（艇と一緒に流れる模様がある） |

採用できた走は 0 件。`measure_speed` は結果を `candidate` としてしか返さず、計測値として貯めない。

**必要な精度**：平和島の公式の直線タイム（316R）では、同じレースの6艇の標準偏差は 0.75%、最速と最遅の差は 2.2%。画面の全区間（約1.55秒）に直すと標準偏差 0.012 秒・差 0.034 秒で、**差は約1コマ（0.033秒）ぶん**。中央の短い区間（約0.57秒）では差が 0.012 秒（1/3コマ・約2px）しかなく、測れない。

**次の実験（自動化の前に）**：人が丁寧に読んで、公式と順位が合うかを確かめる。平和島5レース30走を先に固定 → 1080p で線をはさむ前後のコマの艇首位置から按分して読む（公式タイムは見ない）→ 日を変えてもう一度読む。

- 2回の読みの差の標準偏差 0.012 秒以下、かつ公式との順位相関 0.6 以上 → 自動化を続ける（30走は正解データになる）
- 読みの差は小さいが公式と合わない → 測っている区間が公式と違う。区間を変えるか別の指標として扱う
- 読みの差が 0.012 秒を超える → **この画角での伸びの計測はやめる**。公式データのない場、または艇ごとの差が大きい項目（ターン出口〜立ち上がり。未確認）に移す
